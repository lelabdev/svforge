# Tailwind and design-system linting

The scaffold uses two complementary checks. They have different responsibilities
and neither replaces the other.

## ESLint: validate generated class names

The generated project installs `eslint-plugin-tailwindcss` and configures
`tailwindcss/no-custom-classname` as an **error**. The plugin reads the real
Tailwind v4 entrypoint at `src/routes/layout.css`, including Skeleton and the
SvelteForge theme, and validates static candidates in Svelte markup and supported
class helpers. A typo or class not generated by the configured design system
therefore fails the project's ESLint lint command (`bun run lint`).

A deliberately registered, human-selected UI library can declare narrow copy-in
component roots beneath `src/lib/components/<library>` in `.svforge.json`. Those
registered roots receive scoped exemptions from both
`tailwindcss/no-custom-classname` and the SVForge design rule; the exemptions do
not apply to the rest of the project. Invalid or broad roots are rejected during
registration.

## `svforge-check.mjs`: enforce SVForge design-system policy

The separate `svforge-check.mjs` checker owns design-system policies that the
Tailwind class-name rule does not cover, including duplicate or incompatible
Skeleton primitives, invented Skeleton-looking utilities, and catalog guidance.
It also reports arbitrary spacing and radius classes as **WARN** by default;
`svforge-check.mjs --strict` makes warnings blocking. This policy is not an
ESLint substitute, and the ESLint plugin does not replace the checker's
arbitrary spacing/radius review.

## Verification

The base template's flat ESLint configuration contains the two rules and the
registered-root overrides. Behavioral coverage verifies that unknown static
classes fail, real Tailwind/Skeleton classes pass, and classes in supported
helpers and Svelte template literals are checked (`tests/tailwind-class-validation.test.ts`).
UI registration and scoped exemptions are covered by `tests/ui-libraries.test.ts`
and `tests/eslint-design-system.test.ts`.

Run the repository checks with:

```bash
bun run lint
bun run test
```

The real scaffold validation is `bash scripts/test-scaffold.sh base`. Release CI
runs the complete nine-profile scaffold matrix before publication; ordinary PR
CI does not run that release matrix. See `.github/workflows/publish.yml` for the
current release gate.
